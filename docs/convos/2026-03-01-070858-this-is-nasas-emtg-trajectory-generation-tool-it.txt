● Now let me propose approaches. Based on the research, there are really two
  main architectural approaches:

  Proposed Approaches

  Approach A: TNLP Adapter Inside NLP_interface Subclass (Recommended)

  Create two classes:
  1. IPOPT_interface — inherits from NLP_interface, implements run_NLP(). This
  is the EMTG-facing class.
  2. EMTG_IPOPT_NLP — inherits from Ipopt::TNLP, acts as an internal adapter.
  Translates EMTG's combined F/G arrays into IPOPT's separated
  objective/constraint/gradient/Jacobian calls.

  The adapter lives inside IPOPT_interface as an internal detail. From EMTG's
  perspective, you create an IPOPT_interface the same way you create a
  SNOPT_interface.

  Pros: Clean separation, mirrors SNOPT pattern (snoptProblemExtension is
  analogous), EMTG code only interacts with NLP_interface API.
  Cons: Two classes to maintain.

  Approach B: Single Class Inheriting Both

  Create one class IPOPT_interface that inherits from both NLP_interface and
  Ipopt::TNLP.

  Pros: Single class, fewer files.
  Cons: Multiple inheritance with two large base classes is messy. Method name
  collisions likely. Harder to reason about. Doesn't mirror the SNOPT pattern.

  Approach C: Template/Policy-based Solver

  Create a templated solver wrapper that accepts different solver backends.

  Pros: Very generic.
  Cons: Over-engineered for two solvers. Doesn't match EMTG's existing style.
  Harder for domain scientists to understand.

  My recommendation is Approach A. It mirrors the existing SNOPT pattern (where
  snoptProblemExtension is an internal adapter class), keeps the EMTG-facing API
   clean, and is the most maintainable.

● Design Section 4: Data Translation (F/G Splitting)

  This is the most critical piece — translating EMTG's SNOPT-style data into
  IPOPT's format.

  EMTG (SNOPT-style):
  - F[0] = objective, F[1..nF-1] = constraints
  - G[] = sparse Jacobian of entire F w.r.t. X (triplet: iGfun[], jGvar[], G[])
  - A[] = linear Jacobian entries (separate, triplet: iAfun[], jAvar[], A[])

  IPOPT needs:
  - eval_f() → scalar F[0]
  - eval_grad_f() → dense gradient of objective (length nX). Built from G
  entries where iGfun[k] == 0, plus A entries where iAfun[k] == 0
  - eval_g() → constraint vector F[1..nF-1] (length m = nF-1)
  - eval_jac_g() → sparse constraint Jacobian. G entries where iGfun[k] > 0,
  with row index shifted by -1. Plus A entries where iAfun[k] > 0.

  Pre-computation during construction of EMTG_IPOPT_NLP:
  1. Partition iGfun/jGvar into two index sets:
    - obj_G_indices — where iGfun[k] == 0 (for grad_f)
    - con_G_indices — where iGfun[k] > 0 (for jac_g)
  2. Same for iAfun/jAvar → obj_A_indices, con_A_indices
  3. Pre-build the constraint Jacobian sparsity pattern (iRow, jCol arrays) with
   shifted row indices
  4. Pre-build a mapping from obj_G_indices to dense grad_f positions

  Evaluation flow:
  1. IPOPT calls eval_f() or eval_g() or eval_jac_g()
  2. Adapter calls problem->evaluate(X, F, G, needG) once (caching to avoid
  re-evaluation when IPOPT calls multiple eval functions for the same x)
  3. Extract the relevant pieces from F and G

  Caching strategy: IPOPT provides a new_x flag in each eval call. When new_x ==
   true, we call problem->evaluate(). When new_x == false, we reuse the cached F
   and G. This prevents redundant evaluations.

● Design Section 5: NLP Chaperone and Feasibility Tracking

  EMTG's NLP chaperone tracks the best feasible solution found during
  optimization. Currently implemented inside SNOPT_user_function() via the
  static callback.

  IPOPT equivalent: The intermediate_callback() method on EMTG_IPOPT_NLP:

  bool intermediate_callback(AlgorithmMode mode, Index iter,
      Number obj_value, Number inf_pr, Number inf_du,
      Number mu, Number d_norm, Number regularization_size,
      Number alpha_du, Number alpha_pr, Index ls_trials,
      const IpoptData* ip_data, IpoptCalculatedQuantities* ip_cq);

  Chaperone logic in the callback:
  1. After each IPOPT iteration, check if current point is feasible (inf_pr < 
  feasibility_tolerance)
  2. If feasible and objective is better than incumbent, update X_NLP_incumbent,
   F_NLP_incumbent
  3. If stop_on_goal_attain and objective meets goal, return false to stop IPOPT
  4. Check time limit — if exceeded, return false
  5. Write intermediate solutions to file if better than global incumbent (for
  MBH animation)

  Key difference: SNOPT's callback provides the full X and F vectors at every
  iteration. IPOPT's intermediate_callback() only provides summary statistics
  (obj_value, inf_pr). To get the full X/F, we use the cached values from the
  most recent eval_f()/eval_g() call, which IPOPT makes just before calling the
  callback.

  finalize_solution() handling:
  - Copies final X, constraint multipliers (lambda), and bound multipliers back
  to NLP_interface storage
  - Sets feasibility metrics based on IPOPT's final constraint violation
  - If chaperone is active and incumbent is better than final point, revert to
  incumbent
